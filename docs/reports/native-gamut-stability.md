# 阶段 2B 补充：修复色域边界数值跳变

2026-10-25。四组暖色 RAW 的修正实现对照通过，但阶段 2 整体仍未完成，原生 RAW/调色/导出界面继续关闭。旧失败记录 native-stage2b.md 和 native-stage2b-warm-failed.json 保留。

## 根因与实际改动

旧 Python 与原生移植都在 float32 OKLab 上进行十轮色度二分搜索。旧 Python 自身也存在不连续：同一高色度像素仅将 L 增加两个 float32 ULP（约 1.19e-7），编码蓝通道就从约 .00789 降至接近零。冻结证据见 gamut-boundary-legacy-proof.json。无锐化、单独白平衡/饱和度的隔离确认问题来自色域决策，而不是行块边缘或锐化 halo。

processing.py 和 native/crates/core/src/develop.rs 同时修复：使用成对 float64 正反色彩矩阵及 cbrt，保持帧存储和最终输出 float32；固定 OKLab 亮度/色相，色度搜索细化为 24 轮；以连续、自适应的内边界替代 -1e-6 判定及粗阶梯。边界留量最多为线性 RGB 的 1e-5，并在黑白端按中性 RGB 余量缩小，避免黑白被错误压缩。原有饱和度保护测试不放宽。

这是对原算法的有意数值修正，不是与旧图像逐位相同的移植。旧九参数冻结语料完整保存在 develop-legacy.json；tools/frozen_reference.py 只从固定 Git 基线 a2a2e0 提取原 Python 文件，已有文件字节不同会拒绝覆盖。基准工具默认仍使用该原始基线；--oracle-mode current 必须显式指定，报告记录模式、源码及二进制 SHA。

## 验证

- 修正后的 Rust 与 Python：12/14 位、全/半尺寸四组暖色+锐化最大误差均小于 0.000007，原定 0.00002 阈值保持，且均小于一个 RGB16 码值。全量报告 native-gamut-corrected-warm.json，原片 SHA 全部不变，无非有限输出。
- 42 组色域边界用独立三次多项式交点求解作为参考，不复用生产二分法；新回归覆盖微扰连续性。tools/generate_colour_reference.py 默认校验，只有 --write 才更新修正语料，永不改写旧语料。
- Rust 19 项通过，1 项真实 RAW fixture 默认显式 ignored（阶段 2A 曾单独运行）；Python 全部 163 项通过，包含两项实拍输入及原 Codex 11 项；Node 31 项通过。构建使用本机 GNU 工具链；新提交 MSVC/双 OS CI 另查，不能继承上次成功。

## 性能与兼容边界

一次修正实现对照中，14 位全尺寸：原生解码约 2.37 秒、调色约 8.08 秒、峰值约 479 MiB；修正 Python 解码约 .87 秒、调色约 13.91 秒、约 757 MiB。半尺寸原生调色约 2.08 秒、124 MiB，修正 Python 约 3.56 秒、254 MiB。原始 Python 暖色调色约 5.5 秒，仍快于当前原生；不能只比较较慢的修正 Python 就宣称性能目标达成。不同运行受频率/负载影响，这些不是统计稳定的结论。

原始 Python 与修正原生的对照另存 native-gamut-legacy-difference.json，其 success=false 表示不能通过旧输出一致性门槛，不能改标为成功。四组最大差异约 .0144–.0629，平均约 4.54e-5–7.04e-5，原片 SHA 均不变；这是有意算法修正带来的输出兼容风险。此差异必须与修正实现的数值一致性分开审阅。连续性和解析边界证明了原缺陷及修复方向，不能代替用户肤色/灰卡/校准显示器上的视觉验收。
